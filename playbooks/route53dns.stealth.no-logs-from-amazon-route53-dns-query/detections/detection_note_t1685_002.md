# Detection Note — T1685.002 (Disable or Modify Tools: Disable or Modify Cloud Log)

**Signal:** a Resolver query log configuration disassociated from a VPC, deleted outright, or a DNS
Firewall rule group removed.

**The unit is the VPC, and the source rule cannot name it.** Query logging is configured once and
then *associated* with each VPC individually, so the VPC is the only meaningful unit of coverage.
The source rule groups by the ingestion pipeline's own application and subsystem labels — which can
tell you a shipper went quiet and never which VPC stopped being logged.

**What the original rule got wrong** — beyond the grouping, three properties of this telemetry make
an absence rule weak, and AWS documents all three.

*Logging is opt-in per VPC, and association is a separate step from creation.* A VPC that was never
associated has always produced nothing, which is indistinguishable from one just silenced. Only a
state sweep separates them, and the absence rule structurally cannot.

*Only unique queries are logged.* AWS: *"VPC Resolver query logging logs only unique queries, not
queries that VPC Resolver is able to respond to from the cache."* A VPC with a small, stable set of
destinations produces very few records once its caches are warm. **Low volume is a normal state
here in a way it is not for most log sources**, so a low-water-mark rule fires on healthy VPCs.

*Delivery delay is a documented state.* `additional_properties.is_delayed` exists precisely to say
*"If there is a delay in delivering the logs"*, with no published maximum. A gap is never
conclusive.

## Disassociation is the case that matters

`DisassociateResolverQueryLogConfig` stops one VPC's logging while the configuration itself
survives. Every other VPC keeps logging, the console shows a healthy resource, and an account-wide
record count barely moves. That is the surgical form of this technique and the one an absence rule
is structurally blind to — a rule watching only `DeleteResolverQueryLogConfig` misses it entirely.

Note the ordering AWS enforces: associations must be removed before a configuration can be deleted.
So a deletion is normally preceded by disassociations, the disassociation rule fires first, and a
deletion arriving *without* preceding disassociation events is worth reading closely.

## Removing DNS Firewall is worse than it looks

The firewall fields — `firewall_rule_action`, `firewall_rule_group_id`, `firewall_domain_list_id` —
are the only place AWS states a verdict in this log source. They are populated *"only if DNS
Firewall found a match for a rule with action set to alert or block"*.

So removing the rule group does two things: it stops the blocking, and it empties the field that
would have recorded it. An analyst reading query logs afterwards sees an empty
`firewall_rule_action`, which correctly means "no match" and reads like "allowed by policy". The
loss of the control and the loss of the evidence that the control existed arrive together.

`UpdateFirewallRuleGroupAssociation` deserves its own attention: changing priority can move a
permissive rule group in front of a blocking one, achieving the same result without deleting
anything at all.

## Response levers

**State beats absence, and answers a question no log can.**
`list-resolver-query-log-config-associations` returns `Status` per association. An association in a
failed state, or a configuration whose destination has become unwritable, delivers nothing while
the console shows the resource — and **no CloudTrail event marks the moment delivery starts
failing**, because nothing is called. Only a scheduled read finds it.

**Two other controls depend on this one.** GuardDuty's DNS findings —
`Trojan:EC2/DNSDataExfiltration`, `Impact:EC2/MaliciousDomainRequest.Reputation` and the rest of
the DNS family — consume Resolver query logs as their data source. So does every rule in
`../route53dns.*`. A VPC without an association has all of them silent simultaneously, and their
silence carries no information.

**And VPC flow logs do not cover the gap.** They explicitly exclude *"Traffic generated by
instances when they contact the Amazon DNS server"*, so there is no second source for this traffic.
When Resolver query logging is off for a VPC, DNS activity there is unrecorded, full stop.

**MITRE:** Verified live 2026-08-30.

**Severity:** high for a disassociation or deletion of query logging and for removal of a DNS
Firewall rule group, medium for a single rule deletion or a priority change.

**GuardDuty:** no coverage of this act — there is no finding type whose resource is a Resolver
configuration. And, as above, this technique degrades GuardDuty's own DNS detections, which makes
"GuardDuty is quiet" actively misleading afterwards.
