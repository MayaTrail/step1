## Attribution and de-identification

**No source, vendor, product, repository or package is named in any file in this project
— including this one.**

`original_rules.yml` departs from the kit's "save the source rule verbatim" instruction
(workflow step 0) deliberately. The originals are packaged in a proprietary format whose
scaffolding — payload field lists, entity labels, product-specific field prefixes,
internal enums and packaging metadata — identifies the source on sight while bearing on
nothing about whether the rules are correct. What is retained is the complete detection
logic: name, priority, type, MITRE label, the Lucene query verbatim, threshold, window and
group-by. Every claim in the "Detection Rule Quality Notes" table in `../PLAYBOOK.md` §2 is
checkable against it.

Two extractor changes were needed for this technique and are shared with the rest of the
corpus:

- The flow-log alert's query and group-by key carried a **product-specific field-name
  prefix** that the extractor's docstring claimed to strip but did not — no earlier
  technique's source rules used that namespace, so the gap had never surfaced. The prefix
  is now removed and the field name under it kept, which is the part that is detection
  logic. The tool builds the prefix pattern from parts rather than spelling it out, so the
  de-identifier does not itself carry the token it exists to remove.
- The alert's window enum had no entry in the extractor's lookup table and was being
  emitted verbatim into a file whose whole purpose is to carry no platform identifiers.
  Window parsing is now a shape rule — a duration word followed by a count — so an
  unmapped enum degrades to a real duration rather than leaking.

Both changes were checked for regression: the inline-policy-grant technique's extract
regenerates byte-identical under the patched extractor.

The shipped `references:` blocks in `detections/` cite public MITRE and AWS documentation
only — a deployed rule travels outside the organisation that wrote it, and an internal path
is not resolvable to whoever receives it.

## A note on the file's shape

`original_rules.yml` is generated by two extractor invocations, the second appending, so
the header comment block appears twice. YAML treats both as comments and the file parses as
one five-element sequence. It is also true of this file, and of the siblings', that
`threshold: 0.0  window: 5m` puts two mapping keys on one line and is therefore not
strictly parseable YAML — a corpus-wide property of the extractor's output format, left
alone rather than fixed here so this technique does not diverge from the rest (rule E5).
The file is read by people and diffed against the shipped rules; nothing parses it.

**Merge test — applied, not assumed. Five source rules, one use case, and four of them are shared
with another directory.** The four `CRS SSRF EC2 Metadata` rules match one Core Rule Set signature
family across the four request components a payload can occupy — URI path, query arguments, body and
cookie. The fifth, `Possible SSRF Attempt (Hit to 169.254.169.254)`, is the network-side view of the
same technique.

**Why the same source rules appear in two directories, and why that is not duplication.** The four
CRS rules are also carried by `../../waf.credential-access.crs-ssrf-ec2-metadata/`, and the two
directories detect different things from them:

- The **WAF** directory covers the **request**: whether the web ACL blocked or allowed it, repetition
  from one client, and probing across several request components. Its response is a WAF-rule
  question.
- **This** directory covers the **outcome**: instance-profile credentials being delivered by IMDSv1,
  a role session appearing from outside the fleet's egress addresses, and one session used from more
  than one source address. Its response is a credential-rotation question.

Only one shipped document overlaps — the inbound request carrying an SSRF signature — and it is the
join between them. Splitting the source rules so that each directory saw only half would leave
neither able to state the relationship, which is the part a responder needs.

**One verified defect worth recording about the network-side rule.** VPC flow logs do **not** capture
traffic to `169.254.169.254`: the link-local metadata address is not a routed destination and does
not appear in flow log records. A rule looking for it in flow logs matches nothing, which is why the
detections here work from the STS and instance-profile session side instead.
