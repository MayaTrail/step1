## Alerts captured

| Alert | Priority | What it matches |
|-------|----------|-----------------|
| Assume Role Policy Was Updated | P2 | `eventName:"UpdateAssumeRolePolicy"`, successful only. No content inspection |
| Unexpected Trusts - Wildcard As Principal | P3 | `UpdateAssumeRolePolicy` or `CreateRole` whose trust document contains a wildcard `Principal` / `AWS` / `Federated` / `Service` value |

The second alert searches **both** `requestParameters.policyDocument` and
`requestParameters.assumeRolePolicyDocument`, ORed. That is correct: `UpdateAssumeRolePolicy`
carries the trust document under `policyDocument` and `CreateRole` carries it under
`assumeRolePolicyDocument`, and the two never co-occur on one event. The hazard is in the
port, not the original — ANDing those two field matches inside a single Sigma selection
block yields a rule that can never fire. See `04-AUTHORING-RULES.md` B4; the shipped
`detections/sigma_t1098_001.yml` keeps them as sibling blocks throughout.

The IAM identity-policy alerts from the same source set (`PutUserPolicy`, `PutRolePolicy`,
`PutGroupPolicy`, `CreatePolicyVersion`, `SetDefaultPolicyVersion`, the `Attach*Policy`
building blocks) belong to the privilege-escalation techniques and are captured in
`../../iam.privilege-escalation.inline-policy-grant/_source/` and
`../../_superseded/aws.privilege-escalation.iam-managed-policy-escalation/_source/`.

## Attribution and de-identification

**No source, vendor, product, repository or package is named in any file in this project
— including this one.**

`original_rules.yml` departs from the kit's "save the source rule verbatim" instruction
(workflow step 0) deliberately. The originals are packaged in a proprietary format whose
scaffolding — payload field lists, entity labels, product-specific field prefixes,
internal enums and packaging metadata — identifies the source on sight while bearing on
nothing about whether the rules are correct. What is retained is the complete detection
logic: name, priority, type, the Lucene query verbatim, threshold, window and group-by.
Every claim in the "Detection Rule Quality Notes" table in `../PLAYBOOK.md` §2 is
checkable against it.

The extract is generated by the shared extractor, never by hand:

```bash
SOURCE_PACKS=<path-to-source-packages> \
  python3 tools/deid_extract.py <PackDir> "Unexpected Trusts" "Assume Role Policy Was Updated" \
  > techniques/iam.persistence.role-trust-backdoor/_source/original_rules.yml
```

The shipped `references:` blocks in `detections/` cite public MITRE and AWS documentation
only — a deployed rule travels outside the organisation that wrote it, and an internal
path is not resolvable to whoever receives it.

**Merge test — applied, not assumed.** Two source rules become one use case. Both match
`UpdateAssumeRolePolicy`; the first is a bare event-name match with no content inspection, the
second adds a wildcard-principal content check on the same event. That is a base rule and a
sharpened rule over one operation, not two techniques — the response is identical (read the trust
policy, restore it, revoke sessions), and the content check is a severity dimension. Shipping them
as two playbooks would duplicate the entire procedure to vary one condition.

**Not merged with the permission-granting siblings.** A trust policy decides *who may assume* a
role; an identity policy decides *what the role may do*. The techniques are complementary rather
than the same — a trust backdoor grants an outside principal the ability to become a role that
already has permissions, which is persistence rather than escalation, and it is why this directory
sits under `persistence` while its siblings sit under `privilege-escalation`. See
`../../iam.privilege-escalation.admin-policy-attached/`,
`../../iam.privilege-escalation.inline-policy-grant/`,
`../../iam.privilege-escalation.policy-version-overly-permissive/` and
`../../iam.privilege-escalation.default-policy-version-reverted/`.

Service ground truth for every `iam.*` playbook is in `../../_ground-truth/iam.md`, audited 2026-08-30.
