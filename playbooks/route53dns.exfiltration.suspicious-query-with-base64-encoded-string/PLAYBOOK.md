# IR Playbook: DNS Tunnelling — payload encoded in subdomains, carried in `TXT` and `NULL` query types

## Classification

| Field | Value |
|-------|-------|
| Incident Type | Exfiltration and command-and-control over DNS (data is encoded into query names and answered by a nameserver the attacker operates) |
| Threat Actor | N/A — single-technique, not actor-attributed |
| Platform | aws |
| Severity | High. DNS resolution is permitted outbound almost everywhere, including from hosts with no other egress, so a tunnel works where every other channel is blocked. Volume is low and slow, which is what makes it survive — and the log records the encoded payload without being able to decode it, so the amount taken is a lower bound rather than a figure. |
| MITRE Tactics | Exfiltration, Command and Control |
| MITRE Techniques | T1048.003 |
| Services in Scope | Route 53 Resolver, Route 53 Resolver DNS Firewall, VPC, GuardDuty, CloudTrail |

**What the technique does:** the attacker registers a domain and points its NS records at a
nameserver they run. Code on a host inside the VPC encodes data — a file, a credential, command
output — into subdomain labels and resolves them: `<chunk1>.<session>.exfil.example`, then
`<chunk2>.<session>.exfil.example`, and so on. The VPC Resolver forwards each lookup to the
attacker's nameserver, which records the payload and answers, often in a `TXT` record carrying the
next command. **No TCP connection to the attacker is ever made from the host.** The channel is the
resolver, and the resolver is allowed.

**Why the usual reflexes miss it.** Egress filtering does not apply — the host talks to the VPC
resolver, which is internal and permitted. VPC flow logs do not help either: they explicitly do not
capture *"Traffic generated by instances when they contact the Amazon DNS server"*. And the obvious
detection, matching an encoding, is one encoder change away from silence — which is what the source
rule does, and it looks for a character DNS cannot even carry.

**Detection thesis:** count **distinct names under one registered domain**. The payload *is* the
subdomain, so a tunnel produces a new name every query whatever the alphabet. That measure is also
the one this log source records most completely, because a new name is always a cache miss.

---

## 1. Preparation

### Prerequisites Before This Incident

**Logging & Visibility**
- **Route 53 Resolver query logging associated with every VPC.** It is opt-in per VPC, and it is
  the only record of DNS traffic to the Amazon resolver — VPC flow logs do not capture it.
  `../route53dns.stealth.no-logs-from-amazon-route53-dns-query/` covers its absence.
- **Route 53 Resolver DNS Firewall** with a rule group associated with every VPC, and an incident
  block list already created and empty. It is the containment for this technique and it cannot be
  built during the incident.
- **GuardDuty enabled**, which produces `Trojan:EC2/DNSDataExfiltration` from these same logs.
  Note the dependency: without the Resolver logs, that finding does not fire either.

**Alerting (must be pre-configured)**
- **500 or more distinct names under one registered domain from one source in an hour, with labels at the protocol maximum → P0**
- **500 or more distinct names under one registered domain from one source in an hour → P1**
- **100 or more distinct names with `TXT`/`NULL` types and a majority `NXDOMAIN` → P1**
- **GuardDuty `Trojan:EC2/DNSDataExfiltration` → P1**

**Response Tooling**
- AWS CLI v2 with break-glass responder credentials; `jq`.
- The DNS Firewall domain list ID for incident blocks, written down.
- A baseline of normal subdomain cardinality per registered domain for the estate. Some legitimate
  domains are genuinely high-cardinality — telemetry endpoints, object storage, CDNs — and the list
  of those is what makes this rule usable.

**Known IOC Baselines**
- The high-cardinality domains that are legitimate, by name. This is the tuning surface and it is
  short.
- Which sources legitimately resolve many distinct names: service discovery, certificate
  transparency monitors, security scanners. Exclude them by source rather than by raising the
  threshold, which would hide the technique rather than the noise.

## 2. Identification

### Detection Triggers (prioritized)

#### HIGH-CONFIDENCE — Always Indicate Compromise

| Priority | Event / Signal | Source | MITRE |
|----------|---------------|--------|-------|
| P0 | ≥ 500 distinct `query_name` under one registered domain from one `srcaddr` in 1h, with a label ≥ 45 characters | Resolver query logs (correlation) | T1048.003 |
| P1 | ≥ 500 distinct `query_name` under one registered domain from one `srcaddr` in 1h | Resolver query logs (correlation) | T1071.004 |
| P1 | ≥ 100 distinct names with `TXT` or `NULL` query types and an `NXDOMAIN` ratio above 0.5 | Resolver query logs | T1071.004 |
| P1 | GuardDuty `Trojan:EC2/DNSDataExfiltration` on a host in scope | GuardDuty | T1048.003 |

#### MEDIUM-CONFIDENCE — May Indicate Compromise

| Priority | Event / Signal | Source | MITRE |
|----------|---------------|--------|-------|
| P2 | ≥ 100 distinct names under one registered domain with labels at the protocol maximum | Resolver query logs | T1048.003 |
| P2 | Sustained `NXDOMAIN` volume from one source outside the search-domain pattern | Resolver query logs | T1568.001 |
| P3 | DNS queries over TCP transport from a host that does not normally use it | Resolver query logs | T1071.004 |

### Detection Rule Quality Notes

The source rule is one regular expression over `query_name` and is fully readable, so every row
below is auditable against `_source/original_rules.yml`.

| Issue | Impact | Correction |
|-------|--------|-----------|
| Matches base64 padding (`=`) | `=` is not part of the DNS preferred syntax — RFC 1035 gives letters, digits and hyphens — which is exactly why tools that put base64 into DNS strip the padding. The rule matches essentially nothing a working tunnel produces, and what it does match is malformed queries | Measure subdomain **cardinality** under a registered domain, which is encoding-agnostic: base64, base32, hex and custom alphabets all produce the same shape because the payload *is* the name |
| Encoding-specific by design | Even corrected to a valid character class, a lexical rule is one encoder change away from silence. The attacker chooses the alphabet; they do not choose whether each query is a new name | The structural measure cannot be evaded without abandoning the technique |
| No `group_by` and a threshold of zero | Every individual match is an alert with no actor, no domain and no aggregation — nothing to act on even when it fires | Group by source for the correlation and by registered domain in the query, because the domain is what gets blocked |
| Ignores the label and name length limits | A DNS label is capped at 63 octets and a name at 255. An encoder maximising payload sits at both, and neither is read | Label length shipped as a component and folded into the verdict alongside cardinality |
| Ignores `query_type`, `rcode` and `transport` | `TXT` and `NULL` carry the most payload; a nameserver answering only for encoded names produces `NXDOMAIN` steadily; TCP transport is unusual for ordinary lookups. All three are in the record and unused | All three shipped as components at low or informational, deliberately not alerting alone, and combined in the KQL verdict |
| No account of the caching rule | AWS logs only unique queries, so volume reasoning about ordinary domains is meaningless across this source. A rule author who does not know that will build thresholds that measure TTL expiry | Stated in the rule header and the note — and used: cardinality is precisely the measure caching cannot suppress, because a new name is always a cache miss |

**Recommended detection — count distinct names, not characters.**

```yaml
# DNS tunnelling and exfiltration through encoded subdomains (T1048.003 / T1071.004)
#
# THE SOURCE RULE LOOKS FOR A CHARACTER DNS DOES NOT CARRY. It matches base64 PADDING —
# `query_name` ending in one or two `=` signs, or containing them before a dot. But `=` is not a
# character of the DNS preferred syntax (RFC 1035: letters, digits and hyphens), which is exactly
# why every tool that stuffs base64 into DNS strips the padding first. The rule therefore matches
# essentially nothing a working tunnel produces, and what it does match is malformed queries.
# A regex is not wrong here; the character class is.
#
# WHAT TUNNELLING ACTUALLY STRAINS IS THE LABEL LIMITS. A DNS label is at most 63 octets and a
# full name at most 255. An encoder maximising payload per query pushes against both, so the
# signals that work are structural rather than lexical:
#   - a label at or near 63 characters
#   - a total name at or near 255 characters
#   - MANY DISTINCT SUBDOMAINS under ONE registered domain — the strongest of the set, because
#     payload is encoded in the name, so each query is a new name by construction
#   - query_type TXT or NULL, which carry the most response payload
#   - rcode NXDOMAIN, from a nameserver that answers only for encoded names
#   - transport TCP, unusual for ordinary lookups and used for larger exchanges
#
# THE CACHE LIMITATION IS AN ADVANTAGE HERE, AND IT IS WORTH STATING PLAINLY. AWS logs only unique
# queries, not cache hits — which makes volume reasoning about ordinary domains meaningless across
# this whole source. Tunnelling encodes data in unique subdomains BY CONSTRUCTION, so every
# tunnelling query is a cache miss and every one is logged. The one traffic class the cache hides
# is the class nobody needed to see, and the cardinality rule below is close to complete.
#
# THE SOURCE RULE ALSO HAS NO group_by AT ALL. With a threshold of zero and no grouping, every
# single match is an alert with no aggregation and no actor. The correlations below group by the
# registered domain, which is the thing to block, and carry the source alongside it.
title: DNS query with a label at the protocol maximum
id: 7a3e14cb-58f0-42d9-b6a7-90c25e3f8471
name: r53dns_oversized_label
status: experimental
description: >-
  A DNS query carried a label at or near the 63-octet limit, or a total name near the 255-octet
  limit. Ordinary hostnames are far below both; an encoder maximising payload per query sits at
  them. This is a base rule for the correlation below and a weak signal alone — one long label is
  a hash in a CDN name as often as it is a tunnel — which is why it carries a low level and feeds
  a cardinality test rather than alerting directly.
references:
  - https://www.rfc-editor.org/rfc/rfc1035
  - https://attack.mitre.org/techniques/T1048/003/
tags:
  - attack.exfiltration
  - attack.t1048.003
logsource:
  product: aws
  service: route53resolver
detection:
  long_label:
    query_name|re: '(^|\.)[A-Za-z0-9-]{45,63}\.'
  condition: long_label
falsepositives:
  - >-
    Content delivery networks, object storage and telemetry endpoints that embed hashes or
    identifiers in hostnames. Extremely common, which is why this rule alerts on nothing by itself.
level: low
---
title: Many distinct subdomains queried under one registered domain
id: b0947f26-3ac1-4e58-81d3-6f207ce5b9a4
status: experimental
description: >-
  One source resolved an unusual number of DISTINCT names under a single registered domain. This is
  the strongest available signal for DNS tunnelling and it does not depend on how the payload is
  encoded — base64, base32, hex or a custom alphabet all produce the same shape, because the data
  IS the subdomain. It is also unusually reliable in this log source: tunnelling generates a new
  name every query, so every query is a cache miss and is logged, while the caching that hides
  repeat lookups of ordinary domains does not apply. group-by is the registered domain because
  that is what gets blocked at the DNS Firewall; the source is carried in the matched records.
references:
  - https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver-query-logs.html
  - https://attack.mitre.org/techniques/T1071/004/
tags:
  - attack.command-and-control
  - attack.exfiltration
  - attack.t1071.004
  - attack.t1048.003
correlation:
  type: value_count
  rules:
    - r53dns_oversized_label
  group-by:
    - srcaddr
  timespan: 1h
  condition:
    field: query_name
    gte: 100
falsepositives:
  - >-
    Service discovery, certificate transparency monitors and security scanners legitimately resolve
    many distinct names. They are a small, nameable set of sources — exclude by srcaddr, and keep
    the threshold rather than raising it.
level: high
---
title: DNS query type associated with payload transport
id: e5c86031-92b7-4d40-a71e-38504bfc2d69
name: r53dns_payload_query_type
status: experimental
description: >-
  A TXT or NULL query. TXT records carry arbitrary text and are the standard downstream channel for
  DNS tunnelling; NULL has essentially no legitimate modern use and its presence is notable on its
  own. Neither is alarming in isolation — TXT underpins SPF, DKIM, DMARC and domain-verification
  checks, all of which are routine — so this ships as a component rather than an alert, and becomes
  interesting when the same source is also driving subdomain cardinality.
references:
  - https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/ResourceRecordTypes.html
  - https://attack.mitre.org/techniques/T1071/004/
tags:
  - attack.command-and-control
  - attack.t1071.004
logsource:
  product: aws
  service: route53resolver
detection:
  payload_type:
    query_type:
      - 'TXT'
      - 'NULL'
  condition: payload_type
falsepositives:
  - >-
    SPF, DKIM, DMARC and domain-ownership verification are all TXT lookups and are constant in any
    estate that sends mail. This is background; it earns attention only alongside cardinality.
level: informational
---
title: Repeated NXDOMAIN responses to one source
id: 1f62d4a9-70e3-4b81-95c0-2ae8137bd506
name: r53dns_nxdomain_volume
status: experimental
description: >-
  A source accumulated responses for names that do not exist. A tunnelling client talking to a
  nameserver that answers only for encoded names produces these steadily, and so does malware
  cycling a domain generation algorithm looking for a live controller. It is also what a typo, a
  decommissioned service or a misconfigured search domain produces, which is why it is a
  medium-level component rather than a finding — its value is as the second signal beside high
  subdomain cardinality, where the pair is very hard to explain innocently.
references:
  - https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver-query-logs-format.html
  - https://attack.mitre.org/techniques/T1568.001/
tags:
  - attack.command-and-control
  - attack.t1568.001
logsource:
  product: aws
  service: route53resolver
detection:
  nxdomain:
    rcode: 'NXDOMAIN'
  condition: nxdomain
falsepositives:
  - >-
    Search-domain suffixing, which produces a failed lookup for every suffix tried before the right
    one. Endemic on Kubernetes nodes in particular, where the default resolv.conf produces several
    NXDOMAIN responses for every external name resolved.
level: medium
```

What this set structurally cannot do: it cannot tell you what was exfiltrated. The names carry the
payload encoded, and decoding needs the encoding and the framing, which the log does not hold. It
cannot name a process — `srcids.instance` reaches a host at best. And it cannot tell you the
firewall allowed anything, because `firewall_rule_action` is populated only on a match.

### Key Investigation Queries

> Queries 1–3 read the Resolver query logs through CloudWatch Logs Insights over the configured log
> group. Field names are the log-record names from `../_ground-truth/route53dns.md` §3.
> **`lookup-events` returns ≤50 events per page** — paginate on `NextToken` or use your log platform for busy windows.

#### Query 1 — Reconstruct: the domain, the source, and the shape

```bash
REGION="us-east-1"
LOG_GROUP="/aws/route53/resolver-query-logs"
SRC="<srcaddr-from-the-alert>"
START=$(date -u -v-24H +%s 2>/dev/null || date -u -d '24 hours ago' +%s)
END=$(date -u +%s)

QID=$(aws logs start-query --log-group-name "$LOG_GROUP" \
  --start-time "$START" --end-time "$END" --region "$REGION" \
  --output text --query queryId \
  --query-string "fields @timestamp, query_name, query_type, rcode, transport, srcids.instance, vpc_id
                  | filter srcaddr = '${SRC}'
                  | stats count() as queries, count_distinct(query_name) as distinct_names
                          by query_type, rcode, vpc_id, \`srcids.instance\`
                  | sort queries desc
                  | limit 100")

until [ "$(aws logs get-query-results --query-id "$QID" --region "$REGION" \
           --output text --query status)" != "Running" ]; do sleep 3; done
aws logs get-query-results --query-id "$QID" --region "$REGION" --output json | \
  jq -r '.results[] | map({(.field): .value}) | add'
```

`distinct_names` approaching `queries` is the signature — a new name almost every time. Ordinary
resolution has many queries per distinct name even after caching, because different hosts resolve
the same popular names. A `TXT` row with a high `NXDOMAIN` count alongside is the classic
tunnel-with-downstream-channel shape.

#### Query 2 — Sweep: which registered domains have anomalous cardinality

```bash
REGION="us-east-1"
LOG_GROUP="/aws/route53/resolver-query-logs"
START=$(date -u -v-24H +%s 2>/dev/null || date -u -d '24 hours ago' +%s)
END=$(date -u +%s)

QID=$(aws logs start-query --log-group-name "$LOG_GROUP" \
  --start-time "$START" --end-time "$END" --region "$REGION" \
  --output text --query queryId \
  --query-string 'fields @timestamp, query_name, srcaddr
                  | parse query_name /(?<reg>[^.]+\.[^.]+)\.?$/
                  | stats count_distinct(query_name) as distinct_names,
                          count_distinct(srcaddr) as sources,
                          count() as queries
                          by reg
                  | sort distinct_names desc
                  | limit 50')

until [ "$(aws logs get-query-results --query-id "$QID" --region "$REGION" \
           --output text --query status)" != "Running" ]; do sleep 3; done
aws logs get-query-results --query-id "$QID" --region "$REGION" --output json | \
  jq -r '.results[] | map({(.field): .value}) | add'
```

The top of this list is CDNs, object storage and telemetry endpoints in any healthy estate — that
is the baseline §1 asks for, and it is the whole tuning surface. What matters is a domain that is
high-cardinality **and unfamiliar**, especially with `sources` equal to one: legitimate
high-cardinality domains are resolved by many hosts, and a tunnel by the host it is running on.

The `parse` takes the last two labels as the registered domain, which is wrong for multi-part public
suffixes like `co.uk` — it merges unrelated domains there and inflates cardinality. That error
direction produces false positives rather than misses, which is the safe way round, and a
public-suffix list is the correct fix where one is available.

#### Query 3 — Inspect: has DNS Firewall seen this domain at all

```bash
REGION="us-east-1"
DOMAIN="<registered-domain-from-Query-2>"

echo "== rule groups associated with VPCs in this Region =="
aws route53resolver list-firewall-rule-group-associations --region "$REGION" --output json | \
  jq -r '.FirewallRuleGroupAssociations[] | "\(.Name)\tvpc=\(.VpcId)\tpriority=\(.Priority)\tstatus=\(.Status)"'

echo
echo "== is the domain in any managed or custom list =="
for L in $(aws route53resolver list-firewall-domain-lists --region "$REGION" --output json | \
           jq -r '.FirewallDomainLists[].Id'); do
  NAME=$(aws route53resolver get-firewall-domain-list --firewall-domain-list-id "$L" \
         --region "$REGION" --output text --query 'FirewallDomainList.Name' 2>/dev/null)
  aws route53resolver list-firewall-domains --firewall-domain-list-id "$L" --region "$REGION" \
    --output json 2>/dev/null | jq -r --arg d "$DOMAIN" --arg n "$NAME" \
    '.Domains[]? | select(test($d)) | "[i] \($d) present in list \($n)"'
done

echo
echo "[!] An empty firewall_rule_action on the query records means DNS Firewall did not MATCH."
echo "    It does NOT mean the query was allowed by policy. If no rule group is associated with"
echo "    the VPC at all, nothing was ever evaluated."
```

#### Query 4 — Identify the host and what else it did

```bash
REGION="us-east-1"
INSTANCE="<instance-from-Query-1>"
SINCE=$(date -u -v-24H +%Y-%m-%dT%H:%M:%SZ 2>/dev/null || date -u -d '24 hours ago' +%Y-%m-%dT%H:%M:%SZ)

aws ec2 describe-instances --instance-ids "$INSTANCE" --region "$REGION" --output json 2>/dev/null | \
  jq -r '.Reservations[].Instances[] |
    "state=\(.State.Name)  type=\(.InstanceType)  profile=\(.IamInstanceProfile.Arn // "<none>")  vpc=\(.VpcId)  subnet=\(.SubnetId)"' \
  || echo "[i] instance not found — expected if the source was Lambda, Fargate, EKS or CloudShell"

echo
echo "== what the instance role did in the same window =="
ROLE=$(aws ec2 describe-instances --instance-ids "$INSTANCE" --region "$REGION" --output json 2>/dev/null | \
  jq -r '.Reservations[].Instances[].IamInstanceProfile.Arn // empty' | awk -F'/' '{print $NF}')
if [ -n "$ROLE" ]; then
  aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=ResourceName,AttributeValue="$ROLE" \
    --start-time "$SINCE" --region "$REGION" --output json | \
    jq -r '.Events[].CloudTrailEvent | fromjson |
      {time: .eventTime, src: .eventSource, event: .eventName, ip: .sourceIPAddress}' | \
    jq -s 'group_by(.src) | map({source: .[0].src, calls: length, events: (map(.event) | unique)})'
fi
```

A host running a DNS tunnel is a compromised host, and the tunnel is rarely the only thing on it.
The instance role's activity in the same window tells you what else the intruder reached — and if
the source was Lambda, Fargate or EKS, `describe-instances` returning nothing is expected rather
than suspicious.

## 3. Containment

### Immediate Actions (first 15 minutes)

Block the domain first — it stops the channel for every host at once, which host-level containment
cannot. Then isolate the host.

> Run every command under the **break-glass responder credentials** from §1.

#### Step 1 — Block the registered domain at DNS Firewall

```bash
REGION="us-east-1"
DOMAIN_LIST_ID="<ir-block-domain-list-id>"
DOMAIN="<registered-domain-from-Query-2>"

if ! aws route53resolver get-firewall-domain-list --firewall-domain-list-id "$DOMAIN_LIST_ID" \
       --region "$REGION" >/dev/null 2>&1; then
  echo "[FAIL] domain list $DOMAIN_LIST_ID not found — this is the §1 prerequisite that cannot be"
  echo "       built during an incident. Fall back to Step 2 and treat the channel as open."
else
  aws route53resolver update-firewall-domains --firewall-domain-list-id "$DOMAIN_LIST_ID" \
    --operation ADD --domains "*.${DOMAIN}" "${DOMAIN}" --region "$REGION" --output json | \
    jq -r '"[OK] \(.Name): \(.Status)"'
  echo "[i] both the apex and the wildcard are added — the payload is in the subdomains, so a"
  echo "    block on the apex alone stops nothing."
fi
```

The wildcard matters more than the apex here: every tunnelling query is for a subdomain, and the
apex may never be queried at all.

#### Step 2 — Confirm the rule group is actually associated with the VPC

```bash
REGION="us-east-1"
VPC_ID="<vpc-from-Query-1>"

ASSOC=$(aws route53resolver list-firewall-rule-group-associations --region "$REGION" \
  --output json | jq -r --arg v "$VPC_ID" \
  '[.FirewallRuleGroupAssociations[] | select(.VpcId == $v and .Status == "COMPLETE")] | length')
[ "$ASSOC" -gt 0 ] && echo "[OK] $VPC_ID has $ASSOC active rule group association(s) — the block applies" \
                   || echo "[FAIL] $VPC_ID has NO active rule group association — the block list is not evaluated there"
```

A block list nothing is associated with blocks nothing. This check is one call and it is the
difference between containment and the appearance of it.

#### Step 3 — Isolate the host, preserving it

Move the instance's network interface to a quarantine security group with no egress, as in
`../vpc.initial-access.possible-ssrf-attempt-hit-to-169254169254/` §3 — the same procedure
applies and is not restated here. Do not terminate: the tunnel implant is on the disk and in
memory, and it is the only evidence of how the host was compromised in the first place.

Note that quarantining does **not** stop DNS resolution on its own if the resolver is reachable
through the VPC's default rules, which is why Step 1 comes first.

#### Step 4 — Treat the data as gone

The distinct-name count is a lower bound on the exchange and the payload cannot be decoded from the
log. Identify what the host had access to — the instance profile's permissions from Query 4, the
data on its volumes, the credentials in its environment — and treat all of it as exfiltrated.
Rotate accordingly. An investigation that tries to establish *how much* left will not succeed, and
the time is better spent on rotation.

## 4. Eradication

### Remove Attacker Access

#### Find the other hosts

Re-run Query 2 without the source filter. A tunnel is usually deployed by something, and the
something usually ran more than once — a second host resolving the same registered domain is the
fastest way to find the rest of the footprint.

#### Rebuild the host rather than cleaning it

The implant is code the attacker chose. Rebuilding from a known-good image is the only reliable
removal, and the forensic copy taken in Step 3 preserves whatever the investigation needs.

#### Close the path that got them there

The tunnel is the exfiltration channel, not the entry. Query 4's role activity and the host's own
logs are where the entry is, and eradicating the tunnel without finding it means the next one
arrives on the same route.

#### Keep or remove the block deliberately

The incident block list entry should either move to a permanent list or be removed with a note. A
forgotten wildcard block becomes an unexplained resolution failure months later.

## 5. Recovery

### Restore Clean State

#### Verify the domain no longer resolves from any VPC

```bash
REGION="us-east-1"
DOMAIN="<registered-domain>"

for V in $(aws ec2 describe-vpcs --region "$REGION" --output json | jq -r '.Vpcs[].VpcId'); do
  N=$(aws route53resolver list-firewall-rule-group-associations --region "$REGION" --output json | \
      jq -r --arg v "$V" '[.FirewallRuleGroupAssociations[] | select(.VpcId == $v and .Status == "COMPLETE")] | length')
  [ "$N" -gt 0 ] && echo "[OK]   $V has an active rule group association" \
                 || echo "[FAIL] $V has none — the block does not apply there"
done
```

#### Verify cardinality has returned to baseline

Re-run Query 2 over the last hour. The blocked domain should be absent or present only with
`NXDOMAIN` responses from the firewall. Its continued presence with successful answers means the
block is not being evaluated for that VPC.

#### Confirm the corrected detection fires

```bash
echo "Synthetic test — the rule MUST fire on:"
echo "  600 distinct query_name values under one registered domain from one srcaddr in an hour,"
echo "  with at least one label of 50+ characters — and NO '=' anywhere in any name"
echo "  (the source rule matches none of this, because it looks for base64 padding)"
echo "The rule MUST NOT fire on:"
echo "  600 queries for the SAME name from one source (ordinary resolution, and mostly cached)"
echo "  600 distinct names spread across 200 different registered domains (browsing)"
```

## 6. Lessons Learned

### Root Cause Analysis

| Finding | Contributing Control Failure |
|---------|------------------------------|
| A host exchanged data with an attacker-controlled nameserver | DNS resolution is permitted outbound from every host by default, and the resolver is internal so egress filtering does not apply |
| The detection never fired | It matched base64 padding, a character DNS labels cannot carry |
| There was no fast way to block the channel | No DNS Firewall rule group with an incident block list existed and was associated with the VPCs |
| The volume of data taken is unknown | The payload is encoded in the names and the log cannot decode it |
| The tunnel ran for an extended period | Low, slow query volume is below any rate threshold, and the shape — distinct names — was not being measured |

### Recommended Guardrails

**Protect the query logging and the firewall that make this visible**

```json
// SCP fragment (wrap in a full {"Version":"2012-10-17","Statement":[ ... ]} document):
{
  "Effect": "Deny",
  "Action": ["route53resolver:DeleteResolverQueryLogConfig",
             "route53resolver:DisassociateResolverQueryLogConfig",
             "route53resolver:DisassociateFirewallRuleGroup",
             "route53resolver:DeleteFirewallRule"],
  "Resource": "*",
  "Condition": { "StringNotLike": { "aws:PrincipalArn": ["arn:aws:iam::*:role/PlatformAutomation"] } }
}
```

**Structural controls**
- Associate a DNS Firewall rule group with every VPC, including an empty incident block list. It is
  the only containment that stops the channel for every host at once, and it must exist beforehand.
- Use the AWS managed domain lists as a baseline rule group. They will not catch a freshly
  registered tunnelling domain, and they catch a great deal else for no ongoing effort.
- Associate Resolver query logging with every VPC and alert on a VPC without an association.
  GuardDuty's DNS findings depend on it too, so a gap here is a gap in two controls.
- Maintain the list of legitimately high-cardinality domains as a reviewed artifact. It is the
  tuning surface for this detection and it changes slowly.

**Detection improvements**
- Measure structure, not encoding. Any lexical rule is one encoder change from silence; distinct-name
  cardinality cannot be evaded without abandoning the technique.
- Know which side of the caching rule each of your Resolver rules sits on. Most volume rules over
  this source are measuring cache misses and implying otherwise; this one measures what it claims.
- Alert on cardinality **with** an unfamiliar registered domain and a single source. Legitimate
  high-cardinality domains are resolved by many hosts; a tunnel by the host running it.

### Technique Reference

| Type | Value |
|------|-------|
| MITRE technique | T1048.003 — Exfiltration Over Alternative Protocol: Exfiltration Over Unencrypted Non-C2 Protocol |
| MITRE tactic | Exfiltration (TA0010), Command and Control (TA0011) |
| Primary API | None — the technique is DNS resolution. Containment uses `route53resolver:UpdateFirewallDomains` |
| Event source | Route 53 Resolver query logs. VPC flow logs do **not** carry this traffic — they explicitly exclude queries to the Amazon DNS server |
| Key discriminator | Distinct `query_name` cardinality under one registered domain from one source. Encoding-agnostic, because the payload is the name |
| Ground-truth signal | The query log records themselves, which are unusually complete here: a new name is always a cache miss, so nothing is suppressed by resolver caching |
| "Was it used" pivot | Not applicable — the queries **are** the exfiltration. The equivalent question is what the host had access to, which is Query 4 |
| Blast radius | Everything the host could read: its volumes, its environment, and everything its instance profile permits |
| Error strings | `rcode` values rather than errors. `NXDOMAIN` at volume is the shape of a nameserver answering only for encoded names; `NOERROR` with `TXT` answers is a live downstream channel |

**MITRE mapping note:** the source carries bare `T1048`. `T1048.003` names the sub-technique
exactly — exfiltration over an unencrypted non-C2 protocol, which is what DNS is here.
`T1071.004 — Application Layer Protocol: DNS` is cited alongside because a tunnel carries traffic in
both directions and the log cannot distinguish exfiltration from command-and-control;
`T1568.001 — Dynamic Resolution: Fast Flux DNS` is carried by the NXDOMAIN component, which is also
the shape of a domain generation algorithm. All verified live 2026-08-30.

### Residual Risk

The amount of data taken is not knowable. The names carry the payload encoded and the log holds the
names, but decoding needs the encoding and the framing, which the log does not record — so the
distinct-name count is a lower bound on the exchange and any byte figure in the incident would be
invented. If the tunnel predates the log retention window, its start is unknown and the scope is
everything the host could ever read. Blocking the domain stops that channel and not the technique:
a new domain costs the attacker a few dollars, and the next one will not be on any list either. And
because Resolver query logging is opt-in per VPC, any VPC without an association ran this entire
technique without producing a single record — and GuardDuty's DNS findings were silent there for
the same reason.
