# Ground truth — Amazon VPC Flow Logs

Audited 2026-08-30 against the AWS VPC User Guide (*Flow log records*, *Flow log limitations*).
Every playbook under `techniques/vpc.*` is written from this file. Anything AWS does not state is
marked **UNVERIFIED** and stays unverified in the shipped files rather than being smoothed over.

Scope: VPC Flow Logs only. Route 53 Resolver query logs are `techniques/route53dns.*`; Network
Firewall alert and flow logs are `techniques/netfw.*`; ALB access logs are `techniques/alb.*`.
Those are different products with different schemas and are **not** absorbed here.

---

## 1. The traffic AWS does not log — quoted in full, because three source rules depend on it

> Flow logs do not capture all IP traffic. The following types of traffic are not logged:
> - Traffic generated by instances when they contact the Amazon DNS server. If you use your own
>   DNS server, then all traffic to that DNS server is logged.
> - Traffic generated by a Windows instance for Amazon Windows license activation.
> - **Traffic to and from `169.254.169.254` for instance metadata.**
> - Traffic to and from `169.254.169.123` for the Amazon Time Sync Service.
> - DHCP traffic.
> - Traffic mirrored source traffic. You will see traffic mirrored target traffic only.
> - Traffic to the reserved IP address for the default VPC router.
> - Traffic between an endpoint network interface and a Network Load Balancer network interface.
> - Address Resolution Protocol (ARP) traffic.
> - Traffic on a short-lived regional NAT gateway, which is deleted a few minutes after creation.
>
> — *Flow log limitations*, Amazon VPC User Guide

**The third bullet ends a use case.** A rule matching `dstaddr: 169.254.169.254` in VPC flow logs
cannot fire, ever, in any account, regardless of configuration. It is not a tuning problem and
not a coverage gap that a different field or a longer window closes — AWS does not write the
record. The SSRF-to-IMDS playbook is built around that fact rather than around the rule.

Two more of these matter operationally. **Amazon DNS traffic is not logged**, so DNS-based
exfiltration to the VPC resolver is invisible here and belongs to Route 53 Resolver query logging.
And **traffic between a VPC endpoint ENI and an NLB ENI is not logged**, so a private-link path
between two services in the estate leaves no flow record at either end.

## 2. Default format is version 2 — and half the interesting fields are not in it

> With the default format, the flow log records include the version 2 fields... You cannot
> customize or change the default format.

Version 2, in order: `version account-id interface-id srcaddr dstaddr srcport dstport protocol
packets bytes start end action log-status`.

| Field | Version | Consequence if the flow log is default-format |
|---|---|---|
| `vpc-id`, `subnet-id`, `instance-id` | 3 | No way to attribute a flow to a VPC or an instance |
| **`tcp-flags`** | **3** | **Every SYN-flood, TCP-flag-anomaly and scan-shape rule matches nothing** |
| `type` (IPv4/IPv6/EFA) | 3 | — |
| **`pkt-srcaddr`, `pkt-dstaddr`** | **3** | The original addresses are unavailable; see §3 |
| `region`, `az-id` | 4 | — |
| `pkt-src-aws-service`, `pkt-dst-aws-service` | 5 | No AWS-service attribution of a peer address |
| **`flow-direction`** | **5** | **Ingress and egress cannot be distinguished** |
| `traffic-path` | 5 | No egress path attribution |
| `reject-reason` | 8 | `BPA` / `EC` rejections indistinguishable from SG/NACL |

And the format is fixed for the life of the subscription:

> After you create a flow log, you can't change its configuration or the flow log record format.
> For example, you can't associate a different IAM role with the flow log, or add or remove
> fields in the flow log record. Instead, you can delete the flow log and create a new one with
> the required configuration.

**So field availability is a preparation-phase decision that cannot be corrected during an
incident.** Every `vpc.*` playbook states the custom format it requires in §1, and every rule that
depends on a non-default field says so in its own header. A rule shipped against a default-format
subscription is not noisy — it is silent, which is worse.

Quota: **250 subscriptions per resource per account.**

## 3. `srcaddr`/`dstaddr` are the interface's view, not the packet's

> If traffic is sent to a network interface and the destination is not any of the network
> interface's IP addresses, the flow log displays the primary private IPv4 address in the
> `dstaddr` field. To capture the original destination IP address, create a flow log with the
> `pkt-dstaddr` field.

> If traffic is sent from a network interface and the source is not any of the network
> interface's IP addresses, the behavior depends on the flow direction. For an egress flow, the
> flow log displays the primary private IPv4 address in the `srcaddr` field. To capture the
> original source IP address, create a flow log with the `pkt-srcaddr` field.

AWS names the two cases that matter: **a NAT gateway**, and **an EKS pod whose address differs
from the node ENI's**. So behind a NAT gateway, a rule grouped on `srcaddr` groups every client
in the VPC into one address, and a rule grouped on `dstaddr` for ingress to an NLB or endpoint
sees the interface, not the target. `pkt-srcaddr`/`pkt-dstaddr` carry the original — and they are
version 3, so they are absent unless the subscription was created with them.

One caveat on those fields, also AWS's:

> For `pkt-srcaddr` and `pkt-dstaddr` fields, if the intermediate layer has Client IP address
> Preservation enabled, this field may show the preserved Client IP instead of the IP address of
> the intermediate layer.

`interface-id` returns `-` for flows associated with a regional NAT gateway; `instance-id` returns
`-` for any requester-managed interface, which includes NAT gateway interfaces.

## 4. `tcp-flags` — a bitmask that omits ACK and is OR-ed across the interval

> The bitmask value for the following TCP flags: FIN — 1, SYN — 2, RST — 4, SYN-ACK — 18. If no
> supported flags are recorded, the TCP flag value is 0. For example, since `tcp-flags` does not
> support logging ACK or PSH flags, records for traffic with these unsupported flags will result
> in `tcp-flags` value 0... If there is a record like SYN+ECE, since SYN is a supported flag and
> ECE is not, the TCP flag value is 2. If for some reason the flag combination is invalid and the
> value cannot be calculated, the value is `-`.

> **TCP flags can be OR-ed during the aggregation interval.** For short connections, the flags
> might be set on the same line in the flow log record, for example, **19 for SYN-ACK and FIN, and
> 3 for SYN and FIN**.

Two consequences, and both kill naive rules:

1. **`tcp-flags == 2` is not "a SYN".** It is "a flow whose OR-ed flags across the whole
   aggregation interval came to exactly SYN". A flood of short-lived connections aggregates to 3
   (SYN+FIN), 6 (SYN+RST), 7, 18, 19, 22 or 23. The correct test is *the SYN bit is set*:
   `tcp-flags` ∈ {2, 3, 6, 7, 18, 19, 22, 23}, or a bitwise `and 2 != 0` where the backend
   supports it.
2. **You cannot detect "SYN without ACK".** ACK is not recorded at all, so a half-open handshake
   and a completed one are not distinguishable from this field. Anything phrased as "SYN and not
   ACK" is describing a field that does not exist.

## 5. `action`, `log-status` and what absence means

> `action` — ACCEPT: the traffic was accepted. REJECT: the traffic was rejected. For example, the
> traffic was not allowed by the security groups or network ACLs, **or packets arrived after the
> connection was closed**.

That final clause is a real false-positive source: normal traffic on a closed connection is
logged as REJECT, so a port-scan rule keyed purely on REJECT volume counts ordinary TCP teardown
races. REJECT does **not** distinguish security-group from NACL denial — `reject-reason`
(version 8) only distinguishes `BPA` and `EC`, and returns `-` for everything else.

> `log-status` — OK: data is logging normally. **NODATA: there was no network traffic to or from
> the network interface during the aggregation interval. SKIPDATA: some flow log records were
> skipped during the aggregation interval.** This might be because of an internal capacity
> constraint, or an internal error.

**NODATA is a record.** An idle interface produces records saying "nothing happened", so a rule
that alerts on *zero records* does not fire on an idle VPC — and equally, a stream full of NODATA
is not evidence that logging is broken. **SKIPDATA means AWS dropped records it had**, so the
absence of a specific flow is never proof that the flow did not occur.

## 6. Timing — aggregation, delivery, and why a five-minute window is unsound

> By default, the maximum aggregation interval is **10 minutes**. When you create a flow log, you
> can optionally specify a maximum aggregation interval of 1 minute.

> When a network interface is attached to a Nitro-based instance, the aggregation interval is
> **always 1 minute or less**, regardless of the specified maximum aggregation interval.

> The flow log service typically delivers logs to CloudWatch Logs in about **5 minutes** and to
> Amazon S3 in about **10 minutes**. However, log delivery is on a best effort basis, and your
> logs might be delayed beyond the typical delivery time.

> `start` — The time, in Unix seconds, when the first packet of the flow was received within the
> aggregation interval. This might be either **up to 60 seconds before** the packet was received
> on the network interface or **up to 60 seconds after** the packet was transmitted.

So: a threshold rule with a window shorter than the aggregation interval is not measuring what it
claims. On a default 10-minute aggregation, a 5-minute window sees either zero buckets or one,
and a count threshold tuned against it is meaningless. Add delivery latency on top and the
earliest sound alerting window is roughly **aggregation + delivery**, i.e. 15–20 minutes for a
default-format S3 subscription, or ~6 minutes for a 1-minute Nitro subscription to CloudWatch
Logs. And because `start` carries ±60 seconds of slop, **sub-minute ordering between two flow
records is not evidence of anything.**

## 7. `flow-direction`, `traffic-path`, `protocol`

`flow-direction` (v5): `ingress` | `egress`, relative to the interface that captured the flow.
Without it, "inbound from the internet" and "outbound to the internet" are the same rule.

`traffic-path` (v5), egress only — check `flow-direction` first:
`1` another resource in the same VPC (including an AWS-managed ENI or Outpost local gateway);
`2` an internet gateway **or** a gateway VPC endpoint; `3` a virtual private gateway;
`4` intra-region VPC peering; `5` inter-region VPC peering; `6` a Local Zone or Wavelength Zone;
`7` a gateway VPC endpoint; `8` an internet gateway. `-` if none apply.
Note that **`2` is ambiguous by documentation** and `7`/`8` are the disambiguated values; a rule
treating `2` as "went to the internet" is wrong for gateway-endpoint traffic to S3 or DynamoDB.

`protocol` is the **IANA protocol number**, not a name: 1 ICMP, 6 TCP, 17 UDP, 58 ICMPv6. A rule
written as `protocol: "TCP"` matches nothing.

`pkt-src-aws-service` / `pkt-dst-aws-service` (v5) resolve a peer address to an AWS service from
the published IP ranges — `S3`, `DYNAMODB`, `EC2`, `CLOUDFRONT`, `ROUTE53_RESOLVER` and others.
Useful for separating "egress to the internet" from "egress to an AWS service", but AWS warns the
ranges overlap and only one code is shown.

## 8. VPC Block Public Access silently removes `bytes`

> If you are using VPC Block Public Access (BPA): Flow logs for VPC BPA do not include skipped
> records. Flow logs for VPC BPA do not include `bytes` **even if you include the `bytes` field in
> your flow log**.

Every volume-threshold rule — data egress, exfiltration, anomalous transfer — reads `bytes`. In a
BPA-enabled VPC that field is not populated, so those rules evaluate against nothing and report
clean. This is stated in the affected playbooks rather than assumed away.

## 9. Metadata fields are approximations, by AWS's own statement

> If a field is not applicable or could not be computed for a specific record, the record displays
> a `-` symbol for that entry. **Metadata fields that do not come directly from the packet header
> are best effort approximations, and their values might be missing or inaccurate.**

That covers `instance-id`, `vpc-id`, `subnet-id`, the AWS-service fields, `traffic-path`, the ECS
fields and the tag fields. Any rule that pivots on one of them must tolerate `-`, and a query that
filters on one is filtering out the records where it could not be computed.

## 11. Where the control plane lives

Flow-log configuration is `ec2.amazonaws.com` in CloudTrail: `CreateFlowLogs`, `DeleteFlowLogs`,
`DescribeFlowLogs`. There is **no** flow-log-specific event source. So "somebody turned off flow
logs" is an EC2 management event, and it is the only reliable signal for that — the absence of
flow records cannot distinguish deletion from an idle VPC (§5) or from delivery lag (§6).

AWS Config records `AWS::EC2::FlowLog` as a resource type, which gives configuration history for
the subscription itself, including the log format that cannot be changed after creation.

## 12. What could NOT be verified

1. **Whether `tcp-flags` OR-ing can produce a value with the SYN bit set for a flow that carried
   no SYN.** AWS documents OR-ing across the interval but not whether flows are keyed such that
   this is possible. The enumerated set in §4 is derived from the documented bit values, not from
   an observed record set.
2. **The exact upper bound on delivery latency.** AWS gives typical figures and says delivery is
   best effort, with no stated maximum. Windows in the shipped rules use the typical figures plus
   the aggregation interval, and say so.
3. **Whether `reject-reason` is populated on all rejections in a v8 subscription** or only for the
   two named causes. AWS documents the two values and `-` for "any other reject reason", which
   implies the field is present but uninformative for SG/NACL denials; that reading is an
   inference, not a quoted statement.
