# Ground truth — Route 53 Resolver query logs

Audited 2026-08-30 against the AWS Route 53 Developer Guide (*Resolver query logging*, *Values that
appear in VPC Resolver query logs*). Every playbook under `techniques/route53dns.*` is written from
this file.

Scope: Route 53 **Resolver** query logging (`route53resolver.amazonaws.com`). Hosted zones and the
registrar are `techniques/route53.*` — a different service, different APIs, different Region model.

---

## 1. The caching rule — and why it cuts one way only

> As is standard for DNS resolvers, resolvers cache DNS queries for a length of time determined by
> the time-to-live (TTL) for the resolver... **VPC Resolver query logging logs only unique queries,
> not queries that VPC Resolver is able to respond to from the cache.**
>
> For example... If the same instance's elastic network interface makes a query for
> accounting.example.com within the TTL of the VPC Resolver's cache, VPC Resolver responds to the
> query from the cache. **The second query is not logged.**

**This destroys volume-based reasoning about ordinary domains.** "How many times did this host
resolve example.com" is unanswerable — the log holds cache misses, not queries. Any rule
thresholding on repeat lookups of a stable name is measuring TTL expiry.

**And it leaves tunnelling and rebinding fully visible**, which is the more useful half. DNS
exfiltration encodes payload in unique subdomains *by construction* — every query is a distinct
name, so every query is a cache miss, so every query is logged. DNS rebinding depends on very
short TTLs, which is the same thing. The one class of traffic the cache hides is the class nobody
needed to see.

## 2. What is and is not captured

Captured: queries originating in the VPCs named by the logging configuration; queries from
on-premises resources arriving through an **inbound** Resolver endpoint; queries leaving through an
**outbound** endpoint for recursive resolution; and the action taken by any DNS Firewall rule.

**Query logging is opt-in per VPC.** A configuration is created and then *associated* with each
VPC. A VPC that was never associated produces nothing, and is indistinguishable from one whose
association was removed.

Destinations: a CloudWatch Logs log group, an S3 bucket, or a Firehose delivery stream.

**This is the complement to VPC flow logs.** Flow logs explicitly do **not** capture *"Traffic
generated by instances when they contact the Amazon DNS server"* — see `vpc.md` §1. Resolver query
logs are the only record of that traffic, and the two sources do not overlap.

## 3. Field list, verbatim names

`version` · `account_id` · `region` · `vpc_id` · `query_timestamp` · `query_name` · `query_type` ·
`query_class` · `rcode` · `answer_type` · `rdata` · `answer_class` · `srcaddr` · `srcport` ·
`transport` · `srcids` · `firewall_rule_group_id` · `firewall_rule_action` ·
`firewall_domain_list_id` · `additional_properties`

Notes that change a rule:

- **`rdata`** — *"The value that VPC Resolver returned in response to the query. For example, for
  an A record, this is an IP address in IPv4 format."* **This is where a rebinding answer appears**,
  and it is a different field from `query_name`. Conflating them conflates two unrelated events.
- **`query_name`** — the name asked for. Present on **every** record, so a rule testing that it
  exists tests nothing.
- **`rcode`** — the DNS response code. `NOERROR` is the common case; `NXDOMAIN` is the shape of
  tunnelling to a nameserver that answers only for encoded names, and of typo-squat probing.
- **`srcids`** — *"IDs of the `instance`, `resolver_endpoint`, and the `resolver_network_interface`
  that the DNS query originated from or passed through."* A nested object, not a scalar.
- **`srcids.instance`** carries a caveat AWS states outright: *"If you see an instance ID in
  Route 53 VPC Resolver query logs which is not visible in your account, it might be because the
  DNS query originated from either AWS CloudShell, AWS Lambda, Amazon EKS, or Fargate console."*
  So grouping by it can produce identifiers nobody can resolve to a host, and an empty
  `describe-instances` for one is not evidence of a fabricated log entry.
- **`srcids.resolver_endpoint`** — *"If you have CNAME records that chain across different
  forwarding rules using different resolver endpoints, query logs show only the ID of the last
  resolver endpoint used in the chain."*
- **`firewall_rule_action`**, `firewall_rule_group_id`, `firewall_domain_list_id` — *"This is
  populated only if DNS Firewall found a match for a rule with action set to alert or block."* So
  an empty value means "no DNS Firewall match", never "allowed by policy", and a rule reading it as
  a verdict is misreading it.
- **`additional_properties.is_delayed`** — *"If there is a delay in delivering the logs."* A
  documented delivery-delay flag, which matters for any absence rule.
- **`transport`** — the protocol used to submit the query. TCP for DNS is unusual for ordinary
  lookups and is the shape of large responses or tunnelling.

`version` is `1.1`; AWS increments the major version for non-backward-compatible changes and the
minor for added fields, so a parser should tolerate new fields and check the major.

## 4. DNS label limits, which are what tunnelling actually strains

DNS labels are at most **63 octets** and a full name at most **255 octets**. The preferred syntax
(RFC 1035) is letters, digits and hyphens — **`=` is not a valid label character**, which is why
encoders that stuff base64 into DNS strip the padding. A rule matching base64 padding in a query
name is matching something well-formed tunnelling never produces.

The signals that do work: label length near 63, total name length near 255, high label cardinality
under one registered domain, `TXT` or `NULL` query types, `NXDOMAIN` responses, and `transport`
being TCP.

## 5. Where the control plane lives

`route53resolver.amazonaws.com` in CloudTrail:
`CreateResolverQueryLogConfig`, `DeleteResolverQueryLogConfig`,
`AssociateResolverQueryLogConfig`, `DisassociateResolverQueryLogConfig`,
plus the DNS Firewall family (`CreateFirewallRule`, `DeleteFirewallRule`,
`AssociateFirewallRuleGroup`, `DisassociateFirewallRuleGroup`, `UpdateFirewallRuleGroupAssociation`).

**Disassociating a configuration from one VPC stops that VPC's logging without deleting anything**,
so a rule watching only deletion misses the common case.

## 7. What could NOT be verified

1. **Whether `rdata` is populated for every answer type**, or only for the types AWS names (A,
   CNAME). The field is described generally; rules here read it and tolerate absence.
2. **The delivery latency bound.** `additional_properties.is_delayed` is documented as a flag; no
   maximum delay is published.
3. **Whether a query answered from the DNS Firewall's own block response is logged with `rcode`
   NXDOMAIN or NOERROR.** AWS documents the firewall fields as populated on alert or block and does
   not state the resulting rcode; rules here do not depend on it.
