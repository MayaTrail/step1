# Ground truth — Application Load Balancer access logs

Audited 2026-08-30 against the AWS ELB User Guide (*Access logs for your Application Load
Balancer*). Every playbook under `techniques/alb.*` is written from this file.

---

## 1. The sentence that constrains every threshold rule in this service

> **Elastic Load Balancing logs requests on a best-effort basis. We recommend that you use access
> logs to understand the nature of the requests, not as a complete accounting of all requests.**

AWS is saying in its own documentation that these logs are a sample, not a ledger. Every source
rule in this pack is a count over a window. A count over an incomplete, best-effort sample is a
lower bound with no stated error, so a threshold tuned against observed volume is tuned against
whatever fraction happened to be delivered that week.

Two further delivery properties compound it:

> Elastic Load Balancing publishes a log file for each load balancer node every 5 minutes. Log
> delivery is eventually consistent. **The load balancer can deliver multiple logs for the same
> period.** This usually happens if the site has high traffic.

So the same request can appear more than once, and duplicates arrive precisely when volume is
high — which is when a threshold rule is closest to firing. **Counts can be both short and
double.** Rules in this service are written on ratios, distinct-value counts and status-code
shapes rather than raw totals wherever possible, and where a raw count is unavoidable it is
labelled as approximate.

## 2. Access logs are off by default, and they are files in S3

> Access logs is an optional feature of Elastic Load Balancing that is **disabled by default**.

The legacy access log destination is an S3 bucket, delivered as gzipped files. AWS now also offers
delivery through CloudWatch Logs, Firehose and S3 via the load balancer's Integrations tab; the
field set below is the access-log field set either way. Nothing about a load balancer's *existence*
implies its requests are recorded.

## 3. The field list, in order, with the positions that matter

All fields are space-delimited. AWS: *"When we add a new field, we add it to the end of the log
entry. As we prepare to release a new field, you might see an additional trailing `-` before the
field is released. Ensure that you configure log parsing to stop after the last documented field."*
A parser that indexes from the end, or that fails on an unexpected trailing field, breaks silently
on an AWS release day.

## 4. `elb_status_code` versus `target_status_code` — the distinction two source rules turn on

`elb_status_code` is what the client received. `target_status_code` is what the application said,
**and it is `-` whenever no connection was established or the target sent no response.**

So:

- `elb_status_code` 4xx with `target_status_code` `-` → **the load balancer answered.** The
  application never saw the request. This is WAF blocking, a fixed-response rule, a rule
  evaluation error, or a malformed request — a perimeter event.
- `elb_status_code` 4xx with `target_status_code` 4xx → **the application answered.** Authorisation
  failures, missing resources, bad input reaching real code — an application event.

A rule counting "4xx" without splitting on that field is counting two unrelated populations, and
the larger one is usually the boring one.

**WAF blocks land in `elb_status_code`.** AWS on the `waf` action: *"If this is the final action,
AWS WAF determined that the request should be rejected. By default, requests rejected by AWS WAF
will be logged as `403` in the `elb_status_code` field. When AWS WAF is configured to reject
requests with a Custom Response Code, the `elb_status_code` field will reflect the configured
response code."* And `target:port` is `-` on a WAF block. So a spike of ALB-side 403s with an
empty target is usually the web ACL working, not an application problem.

## 5. Desync classification — request smuggling, already labelled by AWS

`classification` is `-` for an RFC 7230-compliant request. Otherwise `Acceptable`, `Ambiguous` or
`Severe`, with `classification_reason` carrying the specific defect. The `Severe` set:
`BadContentLength`, `BadHeader`, `BadTransferEncoding`, `BadUri`, `BadMethod`, `BadVersion`,
`MultipleContentLength`, `MultipleTransferEncodingChunked`, `SuspiciousTeClPresent`.
The `Ambiguous` set includes `BothTeClPresent`, `DuplicateContentLength`, `SuspiciousHeader`,
`UndefinedContentLengthSemantics`, `UndefinedTransferEncodingSemantics`, `AmbiguousUri`,
`EmptyHeader`.

`BothTeClPresent`, `MultipleContentLength` and `MultipleTransferEncodingChunked` are the classic
HTTP request-smuggling primitives. AWS is classifying them for free in a field no source rule in
this pack reads.

## 6. `error_reason` — authentication failure is a first-class field

When an `authenticate` action fails, `error_reason` carries one of:
`AuthInvalidCookie`, `AuthInvalidGrantError`, `AuthInvalidIdToken`, `AuthInvalidStateParam`,
`AuthInvalidTokenResponse`, `AuthInvalidUserinfoResponse`, `AuthMissingCodeParam`,
`AuthMissingHostHeader`, `AuthMissingStateParam`, `AuthTokenEpRequestFailed`,
`AuthTokenEpRequestTimeout`, `AuthUnhandledException`, `AuthUserinfoEpRequestFailed`,
`AuthUserinfoEpRequestTimeout`, `AuthUserinfoResponseSizeExceeded`.

**These split into two populations and conflating them is the central defect of the
failed-authentication rule.** `AuthInvalid*` and `AuthMissing*` are about the *request* — a bad or
forged cookie, a missing state parameter, a tampered token — and they map to CloudWatch metric
`ELBAuthFailure`. `Auth*EpRequestFailed`, `Auth*EpRequestTimeout` and `AuthUnhandledException` are
about the *identity provider being unreachable* and map to `ELBAuthError`. The first set is an
attack signal; the second is an IdP outage that will page the on-call at 3am for someone else's
availability problem.

`AuthInvalidStateParam` and `AuthMissingStateParam` deserve their own attention: the `state`
parameter is the OAuth CSRF defence, and requests failing on it are the shape of an authorization
code interception attempt rather than a user with a stale tab.

JWT validation failures carry their own codes (`JWTSignatureValidationError`,
`JWTClaimValueInvalid`, `JWKSRequestFailed` and others), metric `JWTValidationFailureCount`.
`JWTSignatureValidationError` specifically means a token was presented whose signature does not
verify — forged, or signed by the wrong key.

## 7. `actions_executed` values

`authenticate`, `fixed-response`, `forward`, `redirect`, `rewrite`, `waf`, `waf-failed`.
`waf-failed` means the load balancer *could not reach* AWS WAF — the request's disposition then
depends on failure configuration, and a run of these means the web ACL was effectively absent.

## 9. Where the control plane lives

`elasticloadbalancing.amazonaws.com` in CloudTrail. The events that matter for this service:
`ModifyLoadBalancerAttributes` (this is how access logging is turned off —
`access_logs.s3.enabled`), `CreateListener` and `ModifyListener` (protocol and TLS policy),
`DeleteLoadBalancer`, `SetWebACL` / `DisassociateWebACL` on the WAF side.

AWS Config records `AWS::ElasticLoadBalancingV2::LoadBalancer` and `...::Listener`.

## 10. What could NOT be verified

1. **The exact upper bound on delivery latency or loss.** AWS states best-effort and five-minute
   publication with eventual consistency, and gives no maximum or error rate.
2. **Whether duplicate delivery is bounded.** AWS states multiple logs for the same period can be
   delivered and does not bound how many.
3. **Whether `ssl_protocol` can be populated on a `type` of `http`.** The field is documented as
   `-` for non-HTTPS listeners; the two are treated as consistent here, and the plaintext test
   reads `type` primarily with `ssl_protocol` as corroboration rather than requiring both.
