# Ground truth — Amazon S3 bucket-level configuration

Audited 2026-08-30 against the AWS S3 User Guide (*Amazon S3 CloudTrail events*) and the S3 API
Reference (*PutPublicAccessBlock*). Every playbook under `techniques/s3.*` is written from this file.

---

## 1. The CloudTrail event name is NOT the API operation name

> Amazon S3 bucket-level API actions tracked by CloudTrail logging appear as the following event
> names. **In some cases, the CloudTrail event name differs from the API action name.** For example,
> `PutBucketLifecycleConfiguration` is `PutBucketLifecycle`.

The pairs that matter here, taken from AWS's own bucket-level event list:

| API operation | **CloudTrail `eventName`** |
|---|---|
| `PutPublicAccessBlock` | **`PutBucketPublicAccessBlock`** |
| `DeletePublicAccessBlock` | **`DeleteBucketPublicAccessBlock`** |
| `GetPublicAccessBlock` | `GetBucketPublicAccessBlock` |
| `PutBucketLifecycleConfiguration` | `PutBucketLifecycle` |
| `PutObjectLockConfiguration` | `PutBucketObjectLockConfiguration` |

**A rule matching `PutPublicAccessBlock` or `DeletePublicAccessBlock` cannot fire**, because those
are SDK operation names and CloudTrail never emits them for a bucket. This is not a casing problem
or a tuning problem — the string does not occur. Two source rules in this pack are written that way.

Casing is a separate hazard: CloudTrail emits `PutBucketLogging`, not `putbucketlogging`, and a
case-sensitive backend matching the lowercase form matches nothing.

## 2. Bucket scope and ACCOUNT scope are different events

Account-level Block Public Access has its own event names entirely:
`PutAccountPublicAccessBlock`, `DeleteAccountPublicAccessBlock`, `GetAccountPublicAccessBlock`.

And the account setting is not merely a default:

> When Amazon S3 evaluates the `PublicAccessBlock` configuration for a bucket or an object, it
> checks the `PublicAccessBlock` configuration for both the bucket (or the bucket that contains the
> object) and the bucket owner's account... **If the `PublicAccessBlock` configurations are
> different between the bucket and the account, Amazon S3 uses the most restrictive combination of
> the bucket-level and account-level settings.**

So **disabling account-level BPA weakens every bucket in the account at once**, and it produces a
different `eventName` from any bucket-level rule. No source rule in this pack covers it.

## 3. What each PublicAccessBlock flag actually does — and what it does not

Quoted from *PutPublicAccessBlock*. The "does not" halves are the load-bearing part: three of the
four are prospective only, so turning them on does **not** fix an already-public bucket.

- **`BlockPublicAcls`** — "PUT Bucket ACL and PUT Object ACL calls fail if the specified ACL is
  public... **Enabling this setting doesn't affect existing policies or ACLs.**"
- **`BlockPublicPolicy`** — "reject calls to PUT Bucket policy if the specified bucket policy allows
  public access. **Enabling this setting doesn't affect existing bucket policies.**"
- **`IgnorePublicAcls`** — "ignore all public ACLs on this bucket and objects in this bucket.
  **Enabling this setting doesn't affect the persistence of any existing ACLs and doesn't prevent
  new public ACLs from being set.**"
- **`RestrictPublicBuckets`** — "restricts access to this bucket to only AWS service principals and
  authorized users within this account if the bucket has a public policy."

**Consequence for containment:** re-enabling BPA is not remediation on its own. `BlockPublicAcls`
and `BlockPublicPolicy` are gates on *future* writes; only `IgnorePublicAcls` and
`RestrictPublicBuckets` change how an existing configuration is evaluated. A responder who re-enables
BPA and stops may have left a public policy in force.

All four are `Required: No`, so a `PutBucketPublicAccessBlock` request may carry any subset — a rule
requiring all four fields to be present matches fewer events than it should.

## 4. What is a management event and what is not

> Amazon S3 logs all control plane operations as management events.

> By default, CloudTrail logs S3 bucket-level API calls that were made in the last 90 days, but not
> log requests made to objects.

So every rule in this service is a **management-event** rule and works on a default trail.
Object-level operations — `GetObject`, `PutObject`, `PutObjectAcl`, `DeleteObject` and the rest of
the `AWS::S3::Object` list — are **data events, off by default and billable**. `lookup-events`
returns zero for them regardless of whether they happened, so "was the exposed data actually read"
is unanswerable without a data-event trail configured beforehand.

`HeadBucket` is the odd one: AWS notes it "is supported as an Amazon S3 data event in CloudTrail"
despite being bucket-level.

## 5. Two cross-account facts that change what an event proves

> CloudTrail always delivers object-level API logs to the requester (Account B). In addition,
> CloudTrail also delivers the same logs to the bucket owner (Account A) even when the bucket owner
> does not own the object.

> The requester gets the logs along with the email information. However, the bucket owner... **gets
> the CloudTrail log reporting the event. However, the bucket owner doesn't get the ACL
> configuration information, specifically the grantee email address and the grant.**

So for an ACL set by another account, the bucket owner's trail records **that** an ACL call
happened and not **what it granted**. A rule reading grantee detail from the owner's trail is
reading a field that is redacted for exactly the cross-account case that matters most.

## 6. The policy document in the event

`PutBucketPolicy` carries the policy in `requestParameters.bucketPolicy` as the submitted document.
Per `AUTHORING-BRIEF.md` A4, request-side policy documents are **raw JSON, not percent-encoded** —
so a `|contains` match works and a decode step is wrong. Match tokens rather than
punctuation-with-assumed-spacing, because a document submitted via `file://` is pretty-printed.

**UNVERIFIED:** the source pack matches `requestParameters.bucketPolicy.bucket_made_public`. No AWS
documentation describes such a field, and it does not appear in the CloudTrail record contents. It
is treated here as a platform-enriched field rather than an AWS one, which means a rule depending on
it fires only where that enrichment exists — and nowhere else.

## 8. Where the control plane lives

`s3.amazonaws.com` for bucket-level operations; `s3express.amazonaws.com` for directory buckets,
which are a separate namespace and are not covered by any rule here.

AWS Config records `AWS::S3::Bucket` including its policy and public-access-block state, which is
the only source of "what did this look like yesterday" once the trail window passes.

## 9. What could NOT be verified

1. **Whether `requestParameters.bucketPolicy.bucket_made_public` exists in any AWS event.** No AWS
   page describes it; treated as platform enrichment throughout.
2. **Whether a `PutBucketPublicAccessBlock` request omitting a flag clears it or leaves it.** The
   API marks all four `Required: No` and does not state merge-versus-replace semantics for a partial
   document. Rules here read the flags present and do not infer the absent ones.

## 6. The meaning of "public", verified 2026-08-30

Source: https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html

**S3 evaluates a bucket policy as public until proven otherwise.** Verbatim:

> When evaluating a bucket policy, Amazon S3 begins by assuming that the policy is public. It then
> evaluates the policy to determine whether it qualifies as non-public. To be considered non-public,
> a bucket policy must grant access only to fixed values (values that don't contain a wildcard or an
> AWS Identity and Access Management Policy Variable) for one or more of the following:

The enumerated list — and **nothing outside it counts**:

`aws` principal / user / role / service principal · `aws:SourceIp` (CIDR) · `aws:SourceArn` ·
`aws:SourceVpc` · `aws:SourceVpce` · `aws:SourceOwner` · `aws:SourceAccount` · `aws:userid`
(outside the pattern `AROLEID:*`) · `s3:DataAccessPointArn` · `s3:DataAccessPointAccount`

Consequences a detection has to respect:

- A `Principal: "*"` statement conditioned on a **fixed** value of one of those keys is **not**
  public. Matching on `"Principal": "*"` alone over-matches.
- A wildcard **inside the condition value** re-publicises it. AWS's own example:
  `"Condition": {"StringLike": {"aws:SourceVpc": "vpc-*"}}` is **public**;
  `"StringEquals": {"aws:SourceVpc": "vpc-91237329"}` is not.
- A condition on any key **not** in the list — `aws:PrincipalTag/...`, for instance — does not make
  a wildcard-principal policy non-public.
- `aws:SourceIp` ranges broader than `/8` (IPv4) or `/32` (IPv6), excluding RFC1918, are evaluated
  as public.

**One public statement publicises the whole policy, with collateral.** Verbatim: *"statement 3
renders the entire policy public, so `RestrictPublicBuckets` applies. As a result, Amazon S3
disables cross-account access, even though the policy delegates access to a specific account."* So
adding one public statement to a policy that also delegates to a partner account silently breaks
that partner while `RestrictPublicBuckets` is on.

**A successful public `PutBucketPolicy` proves the gate was down.** `BlockPublicPolicy: true`
*"causes Amazon S3 to reject calls to `PutBucketPolicy` if the specified bucket policy allows public
access."* So a public policy write that returned no error is evidence that `BlockPublicPolicy` was
false at that instant — the guardrail state at write time is recoverable from the write itself.

**`GetBucketAcl` returns effective permissions, not the stored ACL.** Verbatim: *"suppose that a
bucket has an ACL that grants public access, but the bucket also has the `IgnorePublicAcls` setting
enabled. In this case, `GetBucketAcl` returns an ACL that reflects the access permissions that
Amazon S3 is enforcing, rather than the actual ACL that is associated with the bucket."* Reading the
ACL back therefore does **not** tell you what the ACL is — a public grant can be present and
invisible, and it becomes live again the moment `IgnorePublicAcls` is turned off.

**There is a scope above the account.** Organization-level Block Public Access exists via AWS
Organizations policies, applies all four settings together, propagates to member accounts and
*overrides* account-level settings. Playbooks that describe the account setting as "the floor" are
one level short; the org policy is the real floor where one is in force.

**IAM Access Analyzer and Block Public Access can disagree.** BPA also validates that the actions in
a statement exist, so `Principal: "*"` on an unsupported action is evaluated as public by BPA and may
not be by Access Analyzer.
