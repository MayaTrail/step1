# Detection Note — T1555.006 (Credentials from Password Stores: Cloud Secrets Management Stores)

**Signal:** one principal successfully reads the values of many distinct Secrets Manager
secrets in a short window, or reaches for the batch-read API at all.

**This is the one credential-theft technique where the log tells you exactly what was
taken.** Its neighbours do not. `ec2:GetPasswordData` is terminal evidence with no
follow-on telemetry; `s3:GetObject` is data-plane and off by default; an SSM
`GetParametersByPath` names a path, not the parameters it returned. Secrets Manager
writes one management event per secret read, naming the secret, and it does so in a
default trail with no data-event configuration. A responder can therefore produce an
exact rotation work-list. What the log never contains is the value — so the exposure is
fully enumerable and completely unrecoverable at the same time.

## The batch fan-out — the fact that reorganises the rules

AWS documents two things that together settle how to count this technique:

- CloudTrail entries page, the `GetSecretValue` entry: *"Generated by the GetSecretValue
  **and BatchGetSecretValue** operations."*
- `BatchGetSecretValue` API reference: *"Secrets Manager generates CloudTrail
  `GetSecretValue` log entries **for each secret you request** when you call this
  action."*

A batch call for twenty secrets therefore produces one `BatchGetSecretValue` event and
up to twenty `GetSecretValue` events. The intuitive worry — that the batch API hides a
bulk drain behind a single event and defeats an event-count threshold — is the opposite
of what AWS does. Counting `GetSecretValue` covers both paths, and it is the count that
matches the eradication work-list.

The corollary is that the two bulk-retrieval source rules were two thresholds on one
drain: the volume rule fired at five calls in five minutes, and the batch rule fired at
a batch of one. They are merged here for that reason (see `../_source/PROVENANCE.md`).

## What the original rules got wrong

**No success filter on the counting rule.** The volume building block matched
`eventName:GetSecretValue` with no `errorCode` condition, so a principal denied on five
secrets raised exactly the alert a principal that read five secrets raised. That is rule
B6, and it matters more here than usual: the count is supposed to *be* the rotation
work-list, and a denial list is not a rotation list.

**Counting events, not distinct secrets.** Five retries of one secret and five distinct
secrets read once each produced the same number. The corrected rule counts distinct
`requestParameters.secretId` values.

**The first-seen rule tracked a field its own target does not carry.** The rule named
"Unfamiliar IAM User Retrieved Secrets" tracked new values of
`userIdentity.sessionContext.sessionIssuer.userName`. `sessionContext` is populated for
requests made with temporary credentials; a principal using long-term IAM user access
keys does not carry it. So the rule named for IAM users cannot track an IAM user — it
sees one perpetual absent value, alerts once, and is silent afterwards. Every rule here
keys on `userIdentity.arn`, and treats `sessionIssuer.userName` as role-name enrichment
only (rule A5).

**A "high number" rule with a threshold of zero.** The batch rule fired on any
`BatchGetSecretValue` at all, with no principal check and no success filter, despite its
name. Firing on the first batch call is defensible — that is what the corrected rule
does — but it needs the success filter and the baseline, or every configuration loader
that adopts the batch API pages someone at 03:00 forever.

**The FLOW rule's description did not match its logic.** Its summary described counting
`GetSecretValue` volume; its logic required a successful `ListSecrets` first. An actor
who already knows the secret names — from infrastructure-as-code, a previous
compromise, or a cross-account ARN — never triggers stage one, so the rule is silent on
the better-prepared attacker. Kept here as a `medium` corroborator, not a primary.

## Counting, and how to size the threshold

There is no emulation behind this corpus, so the shipped threshold is derived from
documented behaviour rather than an observed count:

- `BatchGetSecretValue` returns at most **20** secrets per call (`SecretIdList` maximum
  20 items; `MaxResults` valid range 1–20). One maximal batch therefore produces 20
  countable `GetSecretValue` entries, so any threshold at or below 20 fires on a single
  full batch.
- An application reading its own configuration reads a handful of named secrets, and it
  reads the same ones every time.

`gte: 10` distinct secrets in five minutes sits above the application-bootstrap shape
and below one full batch. Size it against your own inventory: the count of secrets a
workload's role can reach is the right ceiling for that role, and the total from
`ListSecrets` is the ceiling for the account. If a legitimate loader reads twelve
secrets at boot, raise the threshold above twelve *for that role* — do not raise it
account-wide.

## Response levers

The event names the secret; only rotation removes the exposure. Two ordering hazards
make this response go wrong in practice, and both are in `../PLAYBOOK.md` §3:

- The rotation function is itself a Secrets Manager principal. A blanket
  `Deny secretsmanager:*` applied for containment severs the rotation Lambda's own
  `GetSecretValue`/`PutSecretValue`, and every subsequent rotation fails while the
  responder believes rotation is running.
- A cancelled or failed rotation can leave `AWSPENDING` attached to a partial version.
  AWS: *"Failing to clean up a cancelled rotation can block you from starting future
  rotations."* Clear it before re-enabling rotation, or the rotation you ordered never
  happens.

Verify a rotation by comparing the version id carrying `AWSCURRENT` in
`DescribeSecret`'s `VersionIdsToStages` against the pre-incident value. Do not attempt
to verify by reading the value back — you cannot see the old one to compare against, and
a check that cannot fail is worse than no check.

## Error strings

Secrets Manager's documented common-error set spells the authorization failure
`AccessDeniedException`, and also carries `NotAuthorized`. The unsuffixed `AccessDenied`
is **not** in the service's documented set, though an IAM-policy-evaluated denial can
still surface that way in CloudTrail (rule A7) — match all three prefix-tolerantly and
confirm against one real denied event from your own trail. The full set a retrieval path
can throw is `AccessDeniedException`, `NotAuthorized`, `DecryptionFailure`,
`InternalServiceError`, `InvalidParameterException`, `InvalidRequestException`,
`InvalidNextTokenException` (batch pagination only), `ResourceNotFoundException`,
`ThrottlingException`.

`DecryptionFailure` is the interesting one: it means the caller reached the secret but
could not use the KMS key. A run of `DecryptionFailure` across many secrets is a drain
attempt that the key policy stopped, and it belongs in the same investigation.

## GuardDuty

`CredentialAccess:IAMUser/AnomalousBehavior` (default severity Medium, data source
CloudTrail management event) names `GetSecretValue` and `BatchGetSecretValue` in its API
set. It is an ML anomaly model, so treat it as corroboration, never as the control —
it carries no guarantee of firing on a given drain, and it independently confirms that
these calls are management events.

## Severity

**High.** A secrets store is where an organisation deliberately concentrates the
credentials that matter, so bulk retrieval by an unbaselined principal is one hop from
whatever the strongest secret in the set grants — commonly a database master or a
long-lived access key. The merged source rules rated this P2 and P3; P3 for a first-time
principal reading production secret values is too low, because the plaintext leaves AWS
at that moment and nothing after it is recoverable.

**MITRE:** the source maps this to `T1552 — Unsecured Credentials` and `T1555 — Credentials from Password Stores`. The precise sub-technique is `T1555.006 — Credentials from Password Stores: Cloud Secrets Management Stores`; `T1552` is the wrong branch, since a secret retrieved through the intended API is not an unsecured credential. Verified live 2026-08-30.

**GuardDuty:** no finding type is specific to Secrets Manager. The adjacent ones are `UnauthorizedAccess:IAMUser/ResourceCredentialExfiltration.InsideAWS` and `.OutsideAWS`, which fire on credentials retrieved from an AWS resource and used elsewhere, and `CredentialAccess:IAMUser/AnomalousBehavior`, which is a CloudTrail-driven anomaly detector rather than a rule about secrets. Neither covers retrieval volume.
