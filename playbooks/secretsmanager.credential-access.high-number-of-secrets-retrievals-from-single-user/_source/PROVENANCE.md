## Merge decision — three source rules, one playbook

Merged under **`07-TIERS.md` §"When merging is legitimate"**, and both tests apply, each
to a different rule.

### Test 1 — same observable, same response, differing only in threshold or priority

This applies to *Retrieve a High Number of Secrets Manager Secrets* and to *Unfamiliar
IAM User Retrieved Secrets*, and it holds because of a documented AWS behaviour that is
easy to assume backwards.

`BatchGetSecretValue` does **not** collapse a bulk read into a single event. AWS's
CloudTrail entries page lists the `GetSecretValue` entry as *"Generated by the
GetSecretValue **and BatchGetSecretValue** operations"*, and the `BatchGetSecretValue`
API reference states *"Secrets Manager generates CloudTrail `GetSecretValue` log entries
**for each secret you request** when you call this action."* A batch call for twenty
secrets therefore emits one `BatchGetSecretValue` event **and up to twenty
`GetSecretValue` events**.

So the batch rule and the volume building block do not observe two different things.
They observe the same physical drain through the same fan-out: the volume rule counts
the per-secret `GetSecretValue` entries the batch call itself produced, and the batch
rule fires on that same call's summary event. One is set at five calls in five minutes;
the other is set at a batch of one. That is a threshold difference on an identical
observable, which is exactly what test 1 describes, and the priorities differ (P2/P2/P3)
in the way test 1 accommodates — each keeps its own row in §2's trigger table.

*Unfamiliar IAM User Retrieved Secrets* filters `eventName:"GetSecretValue"` with
`NOT _exists_:errorCode` — the identical event shape again — and expresses its threshold
as "no prior occurrence in a 7-day window" instead of "five in five minutes". Same
counter, different scale.

The response test was applied separately and is what decided it. For all three the
containment is the same (revoke the principal's sessions, deny further Secrets Manager
reads without severing the rotation function), the eradication is the same (rotate every
secret whose value was returned, then right-size the read permission), the evidence
limit is the same (CloudTrail names the secret and never the value), and the residual
risk is the same (the plaintext left AWS and is unrecoverable). Not one step of the
procedure differs, so they are one use case at three thresholds.

### Test 2 — a flow rule that is purely a composition of building blocks

*High Number of Secrets Retrievals From Single User* is a two-stage flow whose stages are
both building blocks, adding no observable of its own. Under test 2 it becomes a
correlation document inside this playbook's Sigma rather than a playbook: it ships as the
`temporal_ordered` document *"Secrets Manager inventory enumerated then secret values read
by one principal"* in `../detections/sigma_t1555_006.yml`, at `medium`, with both stages
success-filtered.

`retrieve-a-high-number-of-secrets-manager-secrets` and
`unfamiliar-iam-user-retrieved-secrets` therefore have **no directories of their own**.
They are the P0 and P1 rows in §2 and two rule documents in this directory's Sigma.

## What was NOT merged, and why

| Considered | Verdict |
|------------|---------|
| `../../secretsmanager.discovery.secrets-enumerated/` | **Separate.** `ListSecrets` returns metadata only — AWS documents the response as `SecretList` entries of ARN, name, description, tags, rotation state and timestamps, with the value obtainable only through `GetSecretValue`/`BatchGetSecretValue`. Nothing is disclosed, so the eradication step that dominates this playbook — rotate every secret read — does not exist there at all. Different response, so two use cases. Its observable does appear here as stage one of the flow correlation, and the two playbooks cross-reference |
| `../../secretsmanager.discovery.access-repeatedly-denied/` | **Separate.** Same API family, opposite outcome. A denied read discloses nothing and calls for permission review and principal investigation, not rotation. Merging it would put a denial list and a rotation list in one work-list, which is the specific error the success filter exists to prevent |
| `../../secretsmanager.persistence.secret-value-replaced/` | **Separate.** Writing a secret is not reading one; the response is to restore a value, not to rotate a disclosed one |

## Tier

**Tier 1 (full).** Earned on test 1 of `07-TIERS.md` — *account takeover is reachable in
one further hop* — and test 2 — *the response has ordering that can go wrong*.

Test 1: a secrets store is where an organisation deliberately concentrates the
credentials that matter. Reading its values hands the actor whatever the strongest secret
in the set grants, and a long-lived IAM access key stored as a secret is a direct further
hop into the account. AWS's own classification agrees: GuardDuty places `GetSecretValue`
and `BatchGetSecretValue` in `CredentialAccess:IAMUser/AnomalousBehavior`, described as
the stage "when an adversary is attempting to collect passwords, usernames, and access
keys for your environment".

Test 2: the response contains two ordering hazards that fail silently. The rotation
function is itself a Secrets Manager principal, so a blanket `Deny secretsmanager:*`
applied as containment severs the rotation Lambda's own `GetSecretValue`/`PutSecretValue`
and every subsequent rotation fails while the responder believes rotation is running. And
AWS documents that a cancelled or failed rotation can leave `AWSPENDING` attached to a
partial version, where *"Failing to clean up a cancelled rotation can block you from
starting future rotations"* — so the cleanup has to precede the re-enable, or the
rotation that the whole response depends on never starts.

## The source rules' MITRE labels

Recorded in the extract as `T1552/TA0006` and `T1555/TA0006`, and both are disputed in §6
of `../PLAYBOOK.md`. T1552 (*Unsecured Credentials*) describes credentials left somewhere
they should not be; a secret in Secrets Manager is stored exactly where it belongs and is
taken by an authorised-looking API call. T1555.006 (*Credentials from Password Stores:
Cloud Secrets Management Stores*) is the precise fit and was added by MITRE for this. The
labels are carried in `original_rules.yml` so the dispute is checkable against the extract
rather than taken on the playbook's word.

## A finding about the extractor, not about these rules

*Unfamiliar IAM User Retrieved Secrets* is a **new-value** alert, and the shared extractor
carries no branch for that shape: the extract records its name, priority, type and MITRE
label, and drops its filter query, its tracked keypath and its 7-day window. The rule is
therefore the one entry in this directory that is **not** fully auditable against
`original_rules.yml`, and the fields the Quality Notes table in `../PLAYBOOK.md` §2 argues
about are recorded here instead, from a direct read of the source definition:

- filter — `eventSource:"secretsmanager.amazonaws.com" AND eventName:"GetSecretValue" AND
  NOT <internal-role-exclusion> AND NOT _exists_:errorCode`
- tracked keypath — `userIdentity.sessionContext.sessionIssuer.userName`
- window — 7 days

The tracked keypath is the substance of the defect argued in §2 and in
`../detections/detection_note_t1555_006.md`: `sessionContext` is populated for requests
made with temporary credentials, so a principal using long-term IAM user access keys does
not carry it, and the rule named for IAM users cannot track one. The extractor was left
alone rather than extended mid-run, because it is shared with other work in progress; the
gap is reported upward instead.

The same extractor shape also drops the flow alert's per-stage detail. Its stages are
recorded above by resolving the internal ids against the source definition.

## Attribution and de-identification

**No source, vendor, product, repository or package is named in any file in this project
— including this one.**

`original_rules.yml` departs from the kit's "save the source rule verbatim" instruction
(workflow step 0) deliberately, for the reason given in the authoring brief: the originals
are packaged in a proprietary format whose scaffolding — payload field lists, entity
labels, product-specific field prefixes, internal enums and packaging metadata —
identifies the source on sight while bearing on nothing about whether the rules are
correct. What is retained is the complete detection logic: name, priority, type, MITRE
label, the query verbatim, threshold, window and group-by.

The shipped `references:` blocks in `../detections/` cite public MITRE and AWS
documentation only — a deployed rule travels outside the organisation that wrote it, and
an internal path is not resolvable to whoever receives it.

## A note on the file's shape

`threshold: 0.0  window: 5m` puts two mapping keys on one line and is therefore not
strictly parseable YAML — a corpus-wide property of the extractor's output format, left
alone rather than fixed here so this technique does not diverge from the rest (rule E5).
The file is read by people and diffed against the shipped rules; nothing parses it.

**Merge test — applied, not assumed. Five source rules, one use case.** Two are building blocks
(`Secrets Listed`, `Multiple Password Retrieval Using GetSecretValue`), one is a flow over them, and
the remaining two are a batch-retrieval rule and a first-seen-principal anomaly over the same
operation. That is a base-rule-plus-correlation structure, which is the shape authoring rule **B1**
requires — legacy in-rule aggregation is invalid and volume or sequence logic belongs in a
correlation document over named base rules.

They share one response: identify which secrets were read, rotate them, contain the principal.
Volume, batch and novelty are three **triggers** on that same response, not three use cases, and
`ListSecrets` is kept here rather than split out because its value is as the first half of the
enumerate-then-read correlation — alone it is an unroutable base rule.

One naming defect worth recording: `Retrieve a High Number of Secrets Manager Secrets` is not a
volume rule at all. Its query is `eventName:BatchGetSecretValue` with a threshold of 0 over 5
minutes, so it fires on a **single** batch call. The name describes an intent the logic does not
implement, and a reviewer reading the rule list would reasonably assume volume coverage that only
the sibling rule provides.

**Tier:** 1, on criterion 1 of `07-TIERS.md` — *account takeover is reachable in one further hop*.
